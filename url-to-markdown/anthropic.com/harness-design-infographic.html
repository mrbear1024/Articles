问题背景

为什么朴素的实现方式达不到要求

在长时间代理编码中，我们观察到两种持续存在的失败模式，它们是工具链设计需要解决的核心挑战。

上下文焦虑

随着上下文窗口填满，模型在冗长任务中失去连贯性。更严重的是，模型会过早收尾——它们接近自认为的上下文限制时开始"赶工"。压缩保持了连续性但无法给出全新起点；上下文重置则以结构化交接为代价，提供彻底的清零。

自我评估偏差

当被要求评估自己的工作时，代理总是自信地给予好评——即使质量明显平庸。在设计等主观任务中尤为突出，因为没有二元化的验证方式。将执行者与评判者分离被证明是解决此问题的有力杠杆。

核心创新

受 GAN 启发的生成器-评估器架构

借鉴生成对抗网络的思路，将生成与评估分离为独立代理，形成驱动质量持续提升的反馈循环。

全栈编码

三代理协作架构

规划器扩展意图，生成器按冲刺实现，评估器像真实用户一样测试——每个代理解决前代工具链中观察到的特定缺陷。

P

规划器 Planner 1-4 句提示 → 完整规格

将简短提示扩展为完整产品规格。专注高层次产品上下文与技术方向，避免指定细粒度实现——防止规格错误级联到下游。

  • 野心勃勃的范围设定
  • 寻找机会融入 AI 功能
  • 创建视觉设计语言
▼ 规格传递
G

生成器 Generator React + Vite + FastAPI + PostgreSQL

按冲刺逐功能实现。每个冲刺前与评估器协商"冲刺合约"——定义完成标准。通信通过文件系统进行，保持工作忠于规格。

  • 逐功能冲刺式开发
  • 冲刺结束自我评估后交接 QA
  • 使用 git 进行版本控制
▼ 代码交接 QA
E

评估器 Evaluator Playwright MCP

像真实用户一样点击运行中的应用，测试 UI、API 端点和数据库状态。每个标准有硬性阈值，低于阈值则冲刺失败。

  • 产品深度 · 功能性 · 视觉设计 · 代码质量
  • 具体到代码行级的 bug 报告
  • 不通过则返回生成器重做

评估器实战

评估器捕获的真实 Bug

评估器的发现足够具体，可以直接据此行动——精确到代码行级。仅第 3 个冲刺就有 27 个测试标准。

矩形填充工具应允许点击拖动以填充区域
未通过 — 工具仅在拖动起点/终点放置瓦片，而非填充区域。fillRectangle 函数存在但在 mouseUp 时未正确触发。
用户可以选择并删除已放置的实体生成点
未通过 — LevelEditor.tsx:892 处的 Delete 键处理程序要求同时设置 selection 和 selectedEntityId，但点击实体只设置了后者。
用户可以通过 API 重新排列动画帧
未通过 — PUT /frames/reorder 路由定义在 /{frame_id} 之后。FastAPI 将 'reorder' 匹配为整数并返回 422。
模型演进

当模型变强，工具链如何简化

工具链中的每个组件都编码了"模型无法自己完成什么"的假设。随着 Opus 4.6 发布，这些假设需要被重新压力测试。

V1 · OPUS 4.5

完整三代理 + 冲刺分解

规划器 → 生成器（逐冲刺）→ 评估器（逐冲刺）。需要上下文重置应对 Sonnet 4.5 的上下文焦虑。6 小时 / $200。

OPUS 4.6 发布

模型原生能力提升

规划更仔细，长任务持续性更强，更大代码库中更可靠，更好的自查纠错。长上下文检索大幅改善。

V2 · OPUS 4.6

移除冲刺，简化评估

冲刺分解不再必要。评估器改为终评单次通过。生成器连贯运行 2+ 小时无需分解。3 小时 50 分 / $124.70。

关键洞察

评估器的价值是动态的

当任务在模型能力边界内——评估器是多余开销。当任务在边界之外——评估器仍提供真实提升。它不是固定的是/否决定。
